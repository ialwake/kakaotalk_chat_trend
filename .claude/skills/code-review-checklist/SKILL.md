# 코드 리뷰 체크리스트 (카톡 대화 추이 분석기)

구조와 규칙의 기준은 CLAUDE.md다. 이 문서는 리뷰 절차와 리뷰 때 특히 볼 항목만 담는다.

리뷰 대상 파일:
- 로직: `parser.js`, `analyze.js`, `sample.js`
- 화면: `index.html`, `app.js`, `style.css`
- 검증: `test.js`, `scripts/build-check.js`, `eslint.config.mjs`, `package.json`
- Claude Code 설정: `.claude/hooks/*.js`, `.claude/settings.json`, `.claude/agents/*.md`, `.claude/skills/**/SKILL.md`

`*.csv`는 사용자의 실제 개인 대화다. 리뷰 대상이 아니며 어떤 도구로도 열지 않는다(`reviewer-guard.js` 훅이 막는다).

## 절차

1. **범위 정하기**
   - 지정된 파일이나 커밋이 있으면 그것을 본다.
   - 없으면 `git status --short`, `git diff --staged`, `git diff`를 본다. `??`(추적되지 않는 새 파일)도 범위에 넣는다. diff에는 나오지 않기 때문이다.
   - 바뀐 것이 없거나 커밋이 없는 저장소면 위 리뷰 대상 파일 전체를 본다.
2. **자동 검사 실행**: `npm run lint`, `npm run build`, `npm test`를 각각 실행하고 결과(통과/실패, 실패 메시지)를 기록한다. `npm run check`는 첫 실패에서 멈추므로 쓰지 않는다.
3. **읽기**: 바뀐 파일과 새 파일은 diff만 보지 말고 전체를 읽는다. 바뀐 함수를 호출하는 쪽도 Grep으로 찾아 확인한다. Grep에는 항상 `glob`(예: `"*.{js,mjs,css,html,json,md}"`)이나 `type`(예: `"js"`)을 지정한다.
4. **점검**: 아래 체크리스트를 하나씩 확인한다. 의심 가는 동작은 짧은 `node -e` 스크립트에 문자열 입력을 직접 넣어 확인한다(CSV 파일을 읽지 않는다). 파일은 만들지 않는다.
5. **보고**: 맨 아래 형식으로 보고한다. 확인된 문제만 쓰고, 추측은 "확인 필요"로 따로 표시한다.

## 체크리스트

### 정확성
- 오전/오후 12시 경계: `오전 12:xx`는 0시, `오후 12:xx`는 12시여야 한다 (`parser.js` `parseDate`).
- 날짜 계산은 로컬 시간 기준이다. 일수 차이는 `daysBetween`처럼 반올림해서 서머타임에 흔들리지 않아야 한다.
- 월 버킷은 1일 시작, 주 버킷은 **월요일** 시작이다. 대화 없는 기간도 0으로 채워져야 한다(`makeBuckets`).
- 빈 입력, 메시지 1건, 참여자 1명이면 `analyze`가 `null`을 반환하거나 화면이 깨지지 않아야 한다.
- 3명 이상 대화: 상위 2명 외는 `counts[2]`('기타')로 묶이고, 화면에 안내 문구가 나와야 한다.
- CSV: 따옴표 안의 콤마와 개행, `""` 이스케이프, BOM, CRLF, 헤더 없는 파일, 열 순서가 다른 헤더.
- 헤더에서 날짜·보낸사람·메시지 열을 못 찾으면 1~3열로 가정한다(`findColumns`, `COLUMN_NAMES`). 열 이름은 소문자로 바꿔 비교한다.
- `skipped`: 시스템 메시지(`SYSTEM_RE`)와 날짜·이름이 없는 행은 세고, 빈 줄은 세지 않는다.
- 인코딩(`decodeText`): UTF-8 결과에 깨진 글자(U+FFFD)가 있을 때만 EUC-KR로도 읽고, 깨진 글자가 **더 적을 때만** EUC-KR을 고른다. 잘못된 바이트가 한두 개 섞인 UTF-8 파일을 EUC-KR로 바꾸면 한글 전체가 깨진다.

### 보안·개인정보
- 대화에서 온 문자열(이름, 메시지, 파일 첫 줄)은 `h()`의 문자열 자식이나 `textContent`로만 넣는다.
  Grep `innerHTML|outerHTML|insertAdjacentHTML|document\.write` (glob `"*.{js,html}"`)로 찾고, 사용자 데이터가 들어가면 **치명적**이다.
- `h()`의 attrs는 `setAttribute`로 들어간다. 대화 문자열은 `aria-label`·`title`·`data-*` 같은 텍스트 속성에만 넣는다. `href`·`src`·`on*`·`style`에 들어가면 **치명적**이다.
- 외부 요청 금지: `fetch`, CDN 스크립트·폰트, 분석 도구 모두 안 된다. "파일은 브라우저 밖으로 나가지 않는다"는 약속이 깨지면 **치명적**이다.
  `build-check`는 `index.html`의 `<script>`·`<link>`만 막으므로, 나머지는 Grep `fetch\(|XMLHttpRequest|sendBeacon|WebSocket|EventSource|https?://|@import|url\(` (glob `"*.{js,html,css}"`)으로 찾는다. 주석이나 문자열 속 URL은 실제로 요청이 나가는지 따라가서 판단한다.
- 대화 내용을 `console.log`로 남기지 않는다.

### 화면 (`app.js`, `style.css`)
- 결과 영역을 먼저 보이게 한 뒤 차트를 그린다. 축 라벨 간격이 실제 차트 폭으로 정해지므로, 숨긴 채 그리면 폭이 0이 된다.
- 리사이즈 때는 막대를 다시 만들지 않고 `renderAxis()`가 라벨 글자만 다시 쓴다.
- 막대 hover·포커스는 `#chart` 하나에 위임된 리스너가 각 막대의 `aria-label`을 읽어 표시한다. 막대마다 리스너를 붙이지 않는다.
- 색은 `style.css`의 `:root` 토큰을 쓰고, 다크모드(`prefers-color-scheme: dark`)에서도 다시 정의되어야 한다.
- 모바일 폭(375px)에서 페이지 전체에 가로 스크롤이 생기면 안 된다. 차트 영역 안의 스크롤은 괜찮다.
- **브라우저 없이 확인할 수 없는 항목**: 375px 가로 스크롤과 다크모드 가독성은 코드에서 근거(고정 폭, `min-width`, `nowrap`, 다크모드에서 재정의되지 않은 색 등)를 찾은 경우에만 문제로 보고한다. 근거도 반증도 없으면 "문제 없음"으로 단정하지 말고 "확인 필요"에 적는다. 이때 메인 대화에서 `python3 -m http.server 8765 --bind 127.0.0.1`로 띄워 375px·다크모드를 확인하라고 쓴다.

### 프로젝트 규칙
- ES module(`import`/`export`)을 쓰지 않는다. `file://`로 더블클릭해서 열 때 막힌다.
  로직 파일은 IIFE와 `module.exports` 가드 패턴을 유지한다.
- 런타임 의존성을 추가하지 않는다. `package.json`에는 devDependencies(ESLint)만 허용한다.
- 주변 코드처럼 쓴다: 한국어 주석, 짧은 함수, 기존 헬퍼(`h`, `fmtDate`, `num`, `pct`) 재사용.

### Claude Code 설정·검증 도구
- 훅은 `require.main === module`일 때만 `main()`을 실행하고, 아닐 때는 판정 함수만 내보낸다. `test.js`가 require했을 때 npm이 돌거나 stdin을 기다리면 안 된다.
- 막을 때는 exit 2와 stderr 메시지를 쓴다. 다른 0이 아닌 종료 코드는 막지 못하고 그냥 통과된다.
- `pre-commit-check.js`의 감지 정규식을 바꾸면 `test.js`의 감지 사례 표와 속도 테스트도 갱신해야 하고, 둘 다 통과해야 한다. 모든 Bash 호출마다 도는 검사라 되짚기가 폭증하면 안 된다.
- `reviewer-guard.js`의 판정을 바꾸면 `test.js`의 사례 표도 갱신한다. CSV 접근을 놓치는 쪽으로 바뀌면 **치명적**이다.
- `build-check.js`를 바꾸면 외부 참조 금지와 모든 JS의 `node --check`가 유지되어야 한다.

### 테스트
- `parser.js`나 `analyze.js`에 새 분기나 계산이 생기면 `test.js`에 해당 케이스가 있어야 한다. 없으면 **수정 권장**.
- 샘플 데이터 테스트(설계한 공백기 2026.3.9~3.22가 최장 공백기로 잡히는지)가 계속 통과해야 한다.

### 성능
- CSV 파싱은 입력 길이에 대해 O(n)이어야 한다. 메시지마다 배열 전체를 다시 훑는 O(n²) 패턴을 찾는다.
- 주별 차트는 몇 년치 대화면 막대가 수백 개가 된다. 막대마다 불필요한 노드나 리스너를 늘리지 않는다.

## 심각도와 종합 판정

- **치명적**: 잘못된 통계나 파싱 결과, 대화 내용 유출(XSS·외부 요청·`console.log`·CSV 접근), lint·build·test 실패.
- **수정 권장**: 프로젝트 규칙 위반, 새 분기·계산의 테스트 누락, 처리하지 않은 엣지 케이스, 성능 문제.
- **사소함**: 이름·주석·스타일처럼 동작에 영향이 없는 것.
- 종합:
  - 치명적이 하나라도 있으면 최소 "고친 뒤 커밋"이다. 검사 실패는 커밋 훅이 어차피 막는다.
  - 수정 권장만 있으면 "고친 뒤 커밋"과 "커밋해도 됨" 중 하나를 이유와 함께 고른다.
  - 구조가 CLAUDE.md 규칙과 맞지 않으면 "다시 설계 필요"다.

## 보고 형식

```
## 코드 리뷰 결과

검사: lint ✅/❌ · build ✅/❌ · test ✅/❌ (실패 시 핵심 메시지 한 줄)
범위: <리뷰한 파일 또는 diff>

### 치명적 (반드시 고칠 것)
1. `파일:줄` — 문제 한 줄 요약
   - 실패 시나리오: 어떤 입력/상황에서 무엇이 잘못되는지
   - 수정 제안: 구체적으로

### 수정 권장
...

### 사소함
...

### 확인 필요
(직접 확인하지 못한 의심 사항)

종합: 커밋해도 됨 / 고친 뒤 커밋 / 다시 설계 필요 — 이유 한 줄
```

해당 항목이 없는 섹션은 "없음"이라고 쓴다. 칭찬이나 요약 반복은 넣지 않는다.
